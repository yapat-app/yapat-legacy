# Backend API

YAPAT exposes a RESTful API built on **FastAPI**. All endpoints communicate using JSON, and every non-authenticated endpoint requires a valid bearer token for access.

This page summarizes the main backend resources and their relationships:

* **Users** authenticate and belong to one or more **Teams**.
* **Teams** own **Datasets**.
* **Datasets** contain **Recordings**, which are segmented into **Snippets**.
* **Snippets** receive **Annotations**, supporting multi-label entries.
* **Training Examples** and **Classifiers** enable similarity search and weakly supervised learning.
* A unified **Feed** endpoint provides sampling-based snippet retrieval.
* **Taxonomy** endpoints connect species names to GBIF identifiers.

Identifiers such as `{id}` are opaque strings generated by the backend.

---

## Authentication and Users

YAPAT implements **bearer-token authentication** (JWT) and optional **invite codes** for secure team membership management.
This approach aligns with standard REST practices and integrates easily with frameworks like **fastapi-users**, **Authlib**, or other OAuth2-compatible providers.

Invite codes function as short-lived, signed tokens that reference a `team_id` and user role, allowing users to join teams without manual database handling. These mechanisms are mature and well-supported across existing libraries.

Users authenticate using email and password credentials, receiving a signed bearer token used for all subsequent API requests:

```text
Authorization: Bearer <token>
```

### User model

```jsonc
User {
  "id": "user-123",
  "email": "user@example.org",
  "name": "Optional Name",
  "created_at": "2025-11-10T21:00:00Z"
}
```

### Endpoints

#### `POST /auth/register`

Registers a new user.

**Request body**

```json
{
  "email": "user@example.org",
  "password": "secret",
  "name": "Optional Name"
}
```

---

#### `POST /auth/login`

Authenticates a user and returns an access token.

**Response**

```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "token_type": "bearer"
}
```

---

#### `GET /me`

Retrieves the authenticated user and their team memberships.

**Response**

```jsonc
{
  "user": { /* User */ },
  "teams": [
    { "id": "team-1", "name": "Team A", "role": "owner" },
    { "id": "team-2", "name": "Team B", "role": "member" }
  ]
}
```

Only authenticated users can access team, dataset, or annotation data.
Unauthorized requests return `401 Unauthorized`.

## Teams and Memberships

Teams are the foundation for collaboration within YAPAT.
Each user can belong to multiple teams, and each team can manage multiple datasets.
Access to all downstream entities—datasets, recordings, snippets, annotations—is scoped by team membership.

### Team model

```jsonc
Team {
  "id": "team-1",
  "name": "My Research Group",
  "created_at": "2025-11-10T21:00:00Z",
  "created_by": "user-123"
}
```

### Membership model

```jsonc
TeamMember {
  "user_id": "user-123",
  "team_id": "team-1",
  "role": "owner"  // or "member"
}
```

### Endpoints

#### `POST /teams`

Creates a new team. The caller becomes the `owner`.

#### `GET /teams`

Lists all teams that the current user belongs to.

#### `GET /teams/{team_id}`

Retrieves details for a specific team.
Accessible only to team members.

#### `POST /teams/{team_id}/join`

Joins an existing team using a secure invite code.
The backend validates the invite token and assigns the user’s role.

### Notes

* **Role-based access control:** owners can manage datasets and memberships; members can contribute annotations and training data.
* **Invite tokens** can be revoked or expired to control access.
* **Future extensions** may include dataset-level permissions and project-specific roles.

## Datasets

Datasets represent collections of recordings grouped under a team, typically corresponding to a specific monitoring deployment, site, or study.
YAPAT does **not** handle the upload or storage of complete datasets.
Instead, it expects a **URL or filesystem path** that points to an existing directory containing audio files.

When a dataset is created, the backend:

1. Registers the dataset and its `source_uri`.
2. Scans the provided directory or storage location (e.g., an S3 bucket, mounted drive, or local folder) for compatible audio files.
3. Registers each discovered audio file as a `Recording`.
4. Automatically generates **snippets using the default `SnippetConfig`** (see below), and registers them as `Snippet` entries.

### Dataset model

```jsonc
Dataset {
  "id": "ds-1",
  "team_id": "team-1",
  "name": "BR-Mamiraua-2025",
  "description": "Mamirauá pilot deployment",
  "source_uri": "/path/to/mamiraua2025/",
  "created_at": "2025-11-10T21:05:00Z"
}
```

* `source_uri` indicates the directory or remote location containing the dataset’s recordings.
* Audio files discovered under this path will be indexed and stored as `Recording` entries.

### Endpoints

* `GET /teams/{team_id}/datasets` — List all datasets for a team.
* `POST /teams/{team_id}/datasets` — Create a new dataset by providing a `source_uri` (directory or remote location). This triggers recording discovery and snippet generation using the default snippet configuration.
* `GET /datasets/{dataset_id}` — Retrieve dataset metadata and scan status.

Recordings, snippets, and annotations are always scoped by dataset ownership.

## Recordings

Recordings represent the **individual audio files** discovered within a dataset’s source directory.
Each recording corresponds to one file identified during dataset scanning and registered with its metadata (e.g., name, duration, sample rate).

### Recording model

```jsonc
Recording {
  "id": "rec-1",
  "dataset_id": "ds-1",
  "name": "stationA_2025-05-01T00-00Z.wav",
  "start_time_utc": "2025-05-01T00:00:00Z",
  "duration_sec": 3600,
  "sample_rate_hz": 48000,
  "storage_key": "/path/to/mamiraua2025/stationA_2025-05-01T00-00Z.wav"
}
```

* `storage_key` points to the exact location of the audio file.
* Metadata may be extracted automatically (e.g., duration, sampling rate) during dataset scanning.

### Endpoints

* `GET /datasets/{dataset_id}/recordings` — List all recordings associated with a dataset.
* `GET /recordings/{recording_id}` — Retrieve metadata for a specific recording.

This design allows flexible integration with both local and cloud storage backends while avoiding the need for large file uploads through the API itself.
In the future, integrating an efficient, non-browser based upload mechanism could be considered.

## Snippets

Snippets are short audio segments (typically 3 seconds) derived from recordings.
They are the primary units for annotation and for all downstream machine-learning workflows.

To make snippet generation **reproducible and configurable**, each snippet is associated with a **snippet configuration** that encodes how it was created (window length, hop, filters, etc.).

In the first version of YAPAT:

* The system ships with a single **default** snippet configuration (e.g. `cfg-default-3s`).
* When a dataset is created, snippets are **automatically generated** for all recordings using this default configuration.
* The schema still allows additional `SnippetConfig`s to be introduced later, producing alternative snippet sets for the same dataset.

### SnippetConfig model

```jsonc
SnippetConfig {
  "id": "cfg-default-3s",
  "dataset_id": null,                  // null for a global default
  "name": "Default 3s / 50% overlap",
  "description": "3-second windows, 50% overlap, full bandwidth",
  "window_duration_sec": 3.0,
  "hop_duration_sec": 1.5,
  "highpass_hz": null,                // optional filters
  "lowpass_hz": null,
  "target_sample_rate_hz": 48000,     // resampling for snippet/embedding, if needed
  "created_at": "2025-11-10T21:00:00Z"
}
```

Future versions may define dataset-specific configurations by setting `dataset_id` to a concrete dataset, producing distinct snippet sets with different spans or filtering parameters.

### Snippet model

```jsonc
Snippet {
  "id": "snip-123",
  "recording_id": "rec-1",
  "snippet_config_id": "cfg-default-3s",
  "start_time_sec": 12.0,
  "end_time_sec": 15.0,
  "status": "unlabeled",              // "unlabeled" | "in_progress" | "labeled"
  "preview_url": "https://…/snip-123.wav"
}
```

The `snippet_config_id` specifies exactly **how** this snippet was produced from the parent recording.
Different configurations imply:

* different snippet spans,
* different embedding sets,
* and potentially distinct annotation sets tied to each configuration.

### Endpoints

* `GET /datasets/{dataset_id}/snippets` — list snippets for a dataset, with optional filters such as `status`, `limit`, and `snippet_config_id`.
* `GET /snippets/{snippet_id}` — retrieve details for a single snippet.
* `GET /datasets/{dataset_id}/snippet_configs` — list snippet configurations relevant to a dataset (including global defaults).

> **Notes**
>
> * A single global default configuration is created and maintained by the system.
> * Dataset creation automatically triggers snippet generation using this default configuration.
>   Future versions may expose explicit endpoints for creating new `SnippetConfig`s and generating additional snippet sets.
> * After snippets are generated, the backend automatically computes **embeddings** for them in the background using the dataset’s default `EmbeddingModel`.

Snippets are mainly served through the **feed** endpoint for labeling and active-learning workflows.

## Embeddings and Embedding Models

Embeddings are **fixed-length numeric vectors** derived from snippets by a trained model (e.g. BirdNET).
They provide the basis for similarity search, classifier training, and active learning.

In the current version of YAPAT:

* The system ships with **one default `EmbeddingModel`** (e.g. `birdnet_v2`).
* When a dataset is created and its snippets are generated, the backend automatically computes embeddings for those snippets using the default model — typically as a **background job**.
* There are no explicit API triggers for embedding generation; the process is internal and asynchronous.

### Design Principles

* The actual **embedding vectors are not returned** by the REST API.
  Only lightweight metadata confirming their existence is exposed.
* All embedding-dependent operations (e.g. `similarity`, `initialize_model`, `validate`, `refine`) rely on these stored vectors.
* Compatibility between an `EmbeddingModel` and `SnippetConfig` must be guaranteed:
  snippets must match the model’s required `input_duration_sec` and `sample_rate_hz`.

### EmbeddingModel model

```jsonc
EmbeddingModel {
  "id": "birdnet_v2",
  "name": "BirdNET v2",
  "description": "3-second windows at 48 kHz, 1024-dimensional embedding",
  "input_duration_sec": 3.0,
  "sample_rate_hz": 48000,
  "embedding_dim": 1024,
  "created_at": "2025-11-10T21:30:00Z"
}
```

* `input_duration_sec` and `sample_rate_hz` define the model’s required snippet characteristics.
  For instance, **BirdNET requires 3-second inputs at 48 kHz**, so only snippets produced with a compatible `SnippetConfig` can be embedded by this model.

### SnippetEmbedding metadata

Embeddings are stored internally (e.g. in a vector store, binary field, or on disk) and not exposed directly.
The public API only provides metadata describing the presence and version of an embedding for a given snippet–model pair.

```jsonc
SnippetEmbedding {
  "snippet_id": "snip-123",
  "embedding_model_id": "birdnet_v2",
  "version": 1,
  "created_at": "2025-11-10T21:35:00Z"
  // embedding vector stored out-of-band, not returned
}
```

Typically, there will be one `SnippetEmbedding` per `(snippet_id, embedding_model_id)` combination.
If the model is updated or re-embedded, `version` is incremented.

### Endpoints (read-only)

* `GET /embedding_models` — list all available embedding models (initially only the default).
* `GET /snippets/{snippet_id}/embeddings` — return metadata for embeddings associated with a given snippet.

Example response:

```json
{
  "snippet_id": "snip-123",
  "embeddings": [
    {
      "embedding_model_id": "birdnet_v2",
      "version": 1,
      "created_at": "2025-11-10T21:35:00Z"
    }
  ]
}
```

### Notes

* Vector data remain **internal**; only metadata are accessible via the API.
* Embeddings are computed automatically during dataset initialization using the default model.
* Future versions may add:

  * `POST /datasets/{dataset_id}/embeddings/generate` for on-demand embedding computation, and
  * support for multiple embedding models, with explicit `embedding_model_id` selection in feed and training endpoints.

## Annotations

Annotations represent individual label assignments applied to snippets.
Each entry links a snippet to one taxon (or sound category), and multiple annotations can coexist for the same snippet—supporting multi-label classification, inter-annotator disagreement, and consensus modeling.

To make dataset-level querying efficient, the `dataset_id` is **denormalized** directly into the `Annotation` record.
This allows fast filtering and export without joining through snippet and recording tables.

### Annotation model

```jsonc
Annotation {
  "id": "ann-101",
  "dataset_id": "ds-1",                 // denormalized for fast lookup
  "snippet_id": "snip-123",
  "gbif_taxon_key": 2420576,
  "scientific_name": "Hyla versicolor",
  "confidence": 0.92,                   // optional annotator confidence
  "created_at": "2025-11-10T21:10:00Z",
  "created_by": "user-42"
}
```

### Endpoints

#### `GET /snippets/{snippet_id}/annotations`

Retrieve all annotations attached to a specific snippet.

---

#### `GET /datasets/{dataset_id}/annotations`

List or export annotations across the entire dataset.

Supports rich filtering and pagination:

```text
GET /datasets/{dataset_id}/annotations?species=2420576,2498293&annotators=user-42,user-17&from=2025-01-01&to=2025-02-01&limit=500
```

**Query parameters**

| Parameter            | Description                                                          |
| -------------------- | -------------------------------------------------------------------- |
| `species`            | Comma-separated GBIF taxon keys to filter by species or higher taxa. |
| `annotators`         | One or more `user_id`s to filter by annotator.                       |
| `from`, `to`         | Optional ISO 8601 timestamps defining the creation time window.      |
| `limit`              | Maximum number of entries to return (for pagination).                |
| `offset` or `cursor` | Pagination control (optional).                                       |

**Response example**

```json
{
  "items": [
    {
      "id": "ann-101",
      "dataset_id": "ds-1",
      "snippet_id": "snip-123",
      "gbif_taxon_key": 2420576,
      "scientific_name": "Hyla versicolor",
      "confidence": 0.92,
      "created_at": "2025-11-10T21:10:00Z",
      "created_by": "user-42"
    },
    {
      "id": "ann-102",
      "dataset_id": "ds-1",
      "snippet_id": "snip-124",
      "gbif_taxon_key": 2498293,
      "scientific_name": "Lithobates catesbeianus",
      "confidence": 0.81,
      "created_at": "2025-11-10T21:12:00Z",
      "created_by": "user-17"
    }
  ],
  "next_cursor": "opaque-token-or-null"
}
```

---

#### `POST /snippets/{snippet_id}/annotations`

Submit one or more annotations for a snippet (batch mode).

**Request body**

```json
[
  {
    "gbif_taxon_key": 2420576,
    "scientific_name": "Hyla versicolor",
    "confidence": 0.92
  },
  {
    "gbif_taxon_key": 2498293,
    "scientific_name": "Lithobates catesbeianus",
    "confidence": 0.81
  }
]
```

---

#### `DELETE /annotations/{annotation_id}`

Remove a single label assignment (e.g., when correcting an error).

---

### Notes

* The denormalized `dataset_id` enables efficient filtering, aggregation, and export operations.
* A `GET /datasets/{dataset_id}/annotations/export` variant may later support CSV or Parquet outputs for downstream ML pipelines.
* Annotations, together with snippet metadata and embeddings, form the primary supervision signal for YAPAT’s weakly supervised and active learning workflows.

## Feed Generation

The **Feed API** is the central mechanism for retrieving snippets according to a chosen sampling strategy.
It supports methods such as random exploration, diversity sampling, similarity search, model initialization, and active learning.

### Endpoint

```text
GET /datasets/{dataset_id}/feed
```

### Description

A feed request returns a ranked list of snippets based on the selected `sampling_method`.
Each method defines its own internal logic (see [Feed Methods](feed-methods.md)) but all share the same request and response structure.

**Common query parameters**

| Parameter         | Type   | Description                                                           |
| ----------------- | ------ | --------------------------------------------------------------------- |
| `sampling_method` | string | The sampling strategy to use (e.g. `random`, `similarity`, `refine`). |
| `limit`           | int    | Maximum number of snippets to return (default 50).                    |
| `cursor`          | string | Opaque pagination token (for scrolling through large results).        |
| `status`          | string | Optional filter by snippet status (`unlabeled`, `labeled`, etc.).     |

### Generic response schema

```jsonc
{
  "items": [
    {
      "snippet": {
        "id": "snip-123",
        "recording_id": "rec-1",
        "start_time_sec": 12.0,
        "end_time_sec": 15.0,
        "preview_url": "https://…/snip-123.wav"
      },
      "recording": {
        "id": "rec-1",
        "name": "stationA_2025-05-01T00-00Z.wav"
      },
      "annotation_summary": {
        "num_annotations": 2,
        "species_counts": { "2420576": 1 }
      },
      "scores": { "similarity": 0.87, "classifier_confidence": 0.95 }
    }
  ],
  "next_cursor": "opaque-token-or-null"
}
```

### Notes

* The feed endpoint always operates within a dataset and respects team membership.
* Embedding-based methods use the dataset’s current **default `EmbeddingModel`** and **`SnippetConfig`**.
* The specifics of each sampling method (e.g., required parameters and behavior) are documented in
  **[Feed Methods](feed-methods.md)**.

## Classifiers

Classifiers are **lightweight manifests** that bundle independent, per-taxon linear heads trained on snippet embeddings.
They are tied to a single **dataset** and a single **EmbeddingModel**; the active/default **SnippetConfig** for the dataset is assumed unless specified otherwise internally.
Predictions are **multilabel** and **independent per class** (one-vs-rest).

### Classifier model

```jsonc
Classifier {
  "id": "clf-2025-01",
  "dataset_id": "ds-1",
  "name": "Frogs v1",
  "embedding_model_id": "birdnet_v2",
  "target_taxa": ["gbif:2420576", "gbif:2498293"],
  "status": "ready"           // "training" | "ready" | "failed"
}
```

**Notes**

* `target_taxa` contains **namespaced identifiers** (e.g., `gbif:2420576`). GBIF is supported now; additional namespaces (e.g., ENVO) may be added later.
* Classifiers are **snapshots** (manifests). They **reuse** existing per-taxon heads when available and **train only missing heads** asynchronously.
* Team access is derived from the classifier’s `dataset_id`; creator/timestamps and detailed lineage are tracked at the head level (internal), not here.

### Endpoints

#### `POST /classifiers`

Create a classifier **manifest** for a set of taxa. The backend reuses any existing per-taxon heads and **asynchronously trains** missing heads.
Returns a classifier with `status="training"`; it transitions to `"ready"` when all required heads are trained.

**Request body (minimal)**

```json
{
  "dataset_id": "ds-1",
  "name": "Frogs v1",
  "embedding_model_id": "birdnet_v2",           // optional; defaults to dataset's current
  "target_taxa": ["gbif:2420576", "gbif:2498293"],

  "annotation_filters": {                        // optional
    "min_confidence": 0.8,
    "annotators": ["user-42"],
    "snippet_status": "labeled"
  },

  "extra_positive_training_example_ids": ["te-1", "te-2"]  // optional
}
```

**Response**

```jsonc
{
  "id": "clf-2025-01",
  "dataset_id": "ds-1",
  "name": "Frogs v1",
  "embedding_model_id": "birdnet_v2",
  "target_taxa": ["gbif:2420576", "gbif:2498293"],
  "status": "training"
}
```

---

#### `GET /classifiers`

List classifiers accessible to the caller (via team membership on the associated dataset).

---

#### `GET /classifiers/{classifier_id}`

Retrieve classifier metadata (same shape as the **Classifier model**).

---

#### `DELETE /classifiers/{classifier_id}`

Deactivate or remove the classifier **manifest**.
This does **not** delete underlying per-taxon heads, which are shared artifacts.

### ClassifierHead (internal, per-taxon)

Per-taxon one-vs-rest linear heads are stored internally and shared across manifests.
They are keyed by dataset and representation to ensure compatibility and reuse.

```jsonc
ClassifierHead {
  "id": "head-ds1-birdnet_v2-cfg-default-3s-gbif:2420576-v1",

  // Scope / compatibility
  "dataset_id": "ds-1",
  "embedding_model_id": "birdnet_v2",
  "snippet_config_id": "cfg-default-3s",
  "taxon_id": "gbif:2420576",
  "version": 1,

  // Artifact (implementation detail; not exposed via REST)
  "weights_uri": "modelstore://.../w_b.bin",
  "artifact_hash": "sha256:…",

  // Minimal lineage / status (kept at head level)
  "trained_at": "2025-11-11T10:05:00Z",
  "trained_by": "user-123",
  "status": "ready",                      // "training" | "ready" | "failed"

  // Metrics (training-set only for now; plan future held-out split)
  "metrics": {
    "train_precision": 0.91,
    "train_recall": 0.84,
    "train_f1": 0.87
  },

  // Compact training summary (optional)
  "training_summary": {
    "annotation_filters": { "min_confidence": 0.8, "annotators": ["user-42"] },
    "num_positive_snippets": 312,
    "num_negative_snippets": 12400,
    "num_extra_training_examples": 2
  }
}
```

**Notes**

* **Uniqueness key:** `(dataset_id, embedding_model_id, snippet_config_id, taxon_id, version)`.
* The REST API does **not** expose head endpoints in v1. Manifests reference and compose heads internally.
* Classifier heads are trained/scored only for snippets produced with a snippet configuration **compatible** with the `EmbeddingModel` (`input_duration_sec`, `sample_rate_hz`).
